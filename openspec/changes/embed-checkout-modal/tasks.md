## 5. Infrastructure gaps found during verification (not anticipated by the original plan)

Verifying 4.1/4.2 against the real remote environment (`agents-dev.hugosantiago.dev`, behind the shared Caddy proxy) surfaced three pre-existing gaps unrelated to the modal's own code, without which the embedded checkout could not work end to end there. All are fixed and verified:

- [x] 5.1 Astro's dev server hardcodes `/@vite/client`, the dev-toolbar entrypoint, and hoisted page `<script src>` tags as unprefixed absolute paths, never honoring `base` — so the modal's own script 404'd in the browser. Fixed by adding scoped `handle` blocks for `/@vite/*`, `/@fs/*`, `/@id/*`, `/src/*`, `/node_modules/*` in the shared `/etc/caddy/Caddyfile`, forwarding to the frontend (127.0.0.1:4321). Verified via curl against the public domain returning 200 instead of 404.
- [x] 5.2 No Stripe webhook endpoint existed at all for this account, and the backend's `/billing/webhook` route wasn't reachable from the internet (no Caddy route, no public port). Fixed by adding a scoped `handle /speech-dashboard-api/billing/webhook { uri strip_prefix /speech-dashboard-api; reverse_proxy 127.0.0.1:8001 }` block to Caddy (only this one path is exposed, not the rest of the backend), and registering a real webhook endpoint in Stripe (`we_1UJHzIGUJ5bWCJoq6dnKdNAD`, events: `checkout.session.completed`, `customer.subscription.created/updated/deleted`) pointing at `https://agents-dev.hugosantiago.dev/speech-dashboard-api/billing/webhook`. `STRIPE_WEBHOOK_SECRET` in `.env` updated to the real signing secret Stripe returned (the previous value was a stale placeholder with no corresponding live endpoint). Verified via a real test payment producing a `200` webhook delivery in backend logs.
- [x] 5.3 The backend's Keycloak service account (`speech-dashboard-backend` client) only had the `manage-users` realm-management role, missing `view-realm` — so `KeycloakAdmin.set_plan` (called from the webhook handler after every successful payment) failed with `403 Forbidden` fetching the target role, meaning the DB's `plan_tier_id` updated correctly but the user's actual Keycloak `plan-*` role — and therefore their session's displayed plan — never did. Fixed by granting `view-realm` to that service account. Verified: after the fix, a replayed webhook event returned `200`, and the `tester` user's Keycloak role mappings show `plan-basica` was actually assigned.
- [x] 5.4 The modal's original `onComplete` handler reloaded the dashboard on a flat 1.5s timeout, which regularly fired before the async webhook had been processed, showing a stale plan/payment history. Replaced with polling: a new `frontend/src/pages/dashboard/plan-status.ts` route (mirrors `checkout.ts`) that the modal script polls every 1.5s (up to 15s) via `data-plan-status-url`/`data-current-plan` attributes on `#checkout-modal`, reloading as soon as the returned plan differs from the pre-checkout plan (or the timeout is hit).
- [x] 5.5 The 5.4 polling still couldn't detect a plan change on an already-open session: `GET /me` (which `plan-status.ts` calls) returned `plan: claims.plan`, sourced from the user's JWT access-token claims — fixed at token issuance and only refreshed when the token itself expires/refreshes (minutes later), not synchronously updated by the webhook the way the DB row and Keycloak role are. So polling would run for the full 15s and time out, never seeing the new plan, on a session that was already open before the payment. Fixed by sourcing `/me`'s `plan` field from the `user_subscriptions` DB row (`subscription.plan_tier_id`) when one exists, falling back to `claims.plan` only for a user with no subscription row yet. `claims.plan` itself is untouched and still used as-is for quota/entitlement enforcement in `usage.py`/`transcription.py` (intentionally stateless per-request checks, not a display concern). Verified: an old session cookie whose JWT still carried `plan-free` correctly received `plan-basica` from both `/dashboard/plan-status` and the full dashboard page after the fix, with no re-login required.
